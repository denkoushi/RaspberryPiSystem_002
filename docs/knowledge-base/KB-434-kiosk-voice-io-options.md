# KB-434: キオスクの音声入出力をどこに持たせるか（個人スマホ・Bluetooth・USB の検討）

- Status: 検討記録（実装なし）。方向性は「各 Pi4 に USB スピーカーフォン」。まず1台で試す
- Scope: キオスク Pi4 の音声入出力、フローティングチャット（Hermes）の音声会話と音声文字入力
- Date: 2026-10-31
- Related: [ADR-20261011-procedure-voice-input](../decisions/ADR-20261011-procedure-voice-input.md)、ブランチ `feat/voice-terminal-kit` の `docs/plans/kit-voice-terminal-execplan.md`（AtomEcho S3R 音声端末。未マージ）

## 背景

チャットボットと音声で会話したい、テキスト入力の代わりに音声で文字入力したい。課題はマイクとスピーカーの用意。別の AI から「利用者の個人スマホを QR で一時的にマイク・スピーカーとして使う」案が出たので、安全面と費用面から検討した。

ユーザーの条件:

- 個人スマホを使うなら、スマホと本システムの双方に害がなく、セキュリティ事故が起きないこと。
- 音声を Apple や Google などの外部へ送らず、本システムと直接通信すること。
- 使い始めの手順は最小にすること（「ページを開く」などの手順は不要）。

## 検討した案と結論

### Bluetooth でスマホをマイク・スピーカーにする → 不可

- スマホは音を送る側の機器で、イヤホンの代わり（受ける側）になる機能は iPhone にない。Android もほとんどの機種で無効。
- 専用アプリなら音声データは送れるが、個人スマホにアプリを入れることになる。iPhone のブラウザは Bluetooth を使えない。
- ペアリングの登録が端末に残り、利用者が入れ替わる使い方に合わない。

### 個人スマホのブラウザ + 一回限りの QR → 技術的には可能、ただし Wi-Fi の分離が厄介で見送り

成り立つ部分:

- スマホに入れるものはない（アプリ、証明書、プロファイル不要）。残るのは Wi-Fi の接続情報と、サイトごとのマイク許可だけ。
- 手順は「QR を読む → マイク許可（初回だけ）→ 話す」。行き先のドメインを毎回同じにすれば、2回目からは許可を聞かれない（Android の Chrome は保持。iPhone の Safari は設定でサイトのマイクを「許可」にする）。マイク許可を完全になくすことはできない。
- QR は一回限り・最初の1台だけ・放置や「終了」で失効。キオスク画面に「接続中」を出して本人を確かめる。
- 通話は WebRTC（ブラウザ内蔵、エコー除去あり）。DGX Spark で「話し終わり検出 → 音声認識 → チャット → 読み上げ」。目標は話し終わりから1〜2秒。
- 汚染スマホ対策: スマホから届くのは受け口1か所だけ。受け口は Pi5 と別の機器に置き、DB を持たせない。照会のみで書き換えはしない。合言葉は一回限りで短命。残るリスクは受け口ソフトの未知の欠陥で、別機器にすることで被害を DGX の音声処理までに抑える。

厄介な点（見送りの理由）:

- 個人スマホを今の業務用 Wi-Fi に入れると、Pi5 やキオスクと同じネットワークになり分離が崩れる。普通の Wi-Fi はパスワードが全台共通なので、音声用だけ一回限りのパスワードにすることもできない。
- 現場の Wi-Fi は「事務所のルーター → 有線 → 中継機能にしたルーター1台 + 中継機1台」。Pi4 は無線接続。家庭用ルーターの来客用ネットワークは中継機能の状態では使えないことが多く、Pi4 に電波を出させる案も Pi4 が無線のため不安定。
- 確実に分けるには、音声用の安い親機を受け口 Pi にだけ有線でつなぎ、受け口 Pi（LAN 2口）を門番にする構成になる（概算2〜3万円）。キオスクが 20〜50台 に増えて現場に散らばると、電波の範囲（Pi 1台で10〜20m 程度）の問題も出る。

### 各 Pi4 に USB スピーカーフォン → 採用の方向

- Bluetooth スピーカーより USB がよい。Pi4 は Bluetooth と Wi-Fi が同じ部品で、無線接続のキオスクでは両方が不安定になる。Bluetooth のマイクは電話並みの音質で、音声認識に不利。50台のペアリング保守も重い。
- 会議用の USB スピーカーフォン（1台5千〜1万円、50台で25〜50万円）。騒がしい場所はヘッドセットも可。
- マイクは画面のボタンを押している間だけ有効にし、使用中は画面に表示する。
- 音声の通信量は小さく、今の Wi-Fi のままで足りる。個人スマホの安全、Wi-Fi 分離、QR の課題はすべて不要になる。
- 次の一手: 1台で現場の騒音の中の聞き取りを試してから台数を決める。

## 既存の計画との関係

- `feat/voice-terminal-kit` の AtomEcho S3R 音声端末の計画（未マージ）で、「内蔵スピーカーは現場には小さすぎる。返答は別の出力が必要」と記録されている。USB スピーカーフォンはその出力の候補になる。
- 音声認識の経路（`apps/web/src/features/voice/voiceTranscription.ts`、`apps/api/src/services/inference/adapters/http-speech-to-text.adapter.ts`）と、工場 GPU での文字起こしの計測は、上の計画と ADR-20261011 にある。USB 方式でも同じ経路を使う想定。

## 別件

- Pi4 を 20〜50台、今のルーター1台と中継機1台でつなぐと通信が詰まりやすい。台数が増える前に、現場の Wi-Fi 自体を見直す必要がある。
