# ADR-20260727: 組立テンプレート新規作成を表示手順基準の1画面ガイドにする

## Context

組立テンプレートエディタは文書集合、表示手順、工程、締付点を一画面で編集できるが、新規作成時の作業順を示していない。機種名だけで保存ボタンが有効になる一方、APIは各工程の締付点とREQUIREDトレーサビリティ条件を要求する。基本設定は閉じた構成ペイン内にあり、業務固有の仮値が完成値のように見える。

文書一覧には独立した上下操作があるが、明示表示手順を保存する場合は表示手順で最初に現れる順へ再計算される。「表示用ボルト仕様」も、呼び径、長さ、材質、強度区分と内容が重なる。ただし既存テンプレートの文字列はExcel出力上の独自表記である可能性がある。

## Decision

1. エディタは一画面・一保存を維持し、「基本設定」「文書と表示手順」「工程と締付点」「確認して保存」の4段階ガイドを常設する。段階は編集順を強制せず、不足項目への移動手段として使う。
2. 保存はWebがAPI必須条件を満たしたと判定した場合だけ可能にする。保存イベントでも再判定し、APIは最終防御として現在の検証を維持する。
3. 白紙新規では機種名、名称、手順パターン、工程識別値、締付条件を空欄にする。手順書IDを指定して開始した場合だけ、その文書と全ページ表示手順を初期化する。指定のない新規URLは公開文書を暗黙選択しない。
4. 明示表示手順があるテンプレートの文書順は、各文書が表示手順へ最初に現れる順から算出する。文書一覧の独立した上下操作を廃止し、未使用文書は保存不可として表示する。文書ラベルは文書集合のメタデータとして維持する。
5. 新しい締付点の表示用ボルト仕様は、呼び径、長さ、材質、強度区分から自動生成する。既存の保存済み文字列はカスタム値として保持し、利用者が明示的に自動生成へ戻せるようにする。
6. 工程は一件以上を維持し、一覧から順序変更と確認付き削除を可能にする。`requireManualAdvance=true`とチェック項目0件許容は変更しない。
7. HTTP API、Prisma schema、migration、Excel列は変更しない。

## Consequences

- 初見利用者は同じ画面内で作成順と不足理由を確認できる。
- 不完全なpayloadをAPIへ送る前に防止でき、WebとAPIの通常時契約が一致する。
- 表示手順順と文書順の競合がなくなる。
- 業務固有の仮値を見落として別製品へ保存する危険が減る。
- 新規のボルト表示名は二重入力が不要になり、既存独自表記の互換性は維持される。
- 適合グループが編集後に外部で無効化される競合は残るため、APIのtransaction内検証を最終権限として維持する。

## Rejected Alternatives

- 段階ごとに別画面へ進む強制ウィザードは、手順書を見ながら工程と締付条件を往復する操作を妨げるため採用しない。
- 現行レイアウトのまま保存エラーだけ増やす案は、作成順が分からない問題を解決しないため採用しない。
- 文書順と表示手順順を独立して永続化する案は、作業者が見る順序と主手順書の意味を再び分岐させるため採用しない。
- 既存の表示用ボルト仕様を無条件に自動文字列へ置換する案は、Excelの独自表記を失うため採用しない。
