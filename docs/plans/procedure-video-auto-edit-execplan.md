# 作業動画の自動編集(場面の区切りと映像からの字幕案)

この ExecPlan は生きた文書である。`Progress`、`Surprises & Discoveries`、`Decision Log`、`Outcomes & Retrospective` は作業の進行に合わせて更新する。書き方は `.agent/PLANS.md` に従う。動画機能そのもの(V1 取込、V2 トリミングとコメント字幕、V3 接続)の設計正本は `docs/plans/procedure-manuals-execplan.md` の「動画: V1 / V2 / V3」であり、この計画はその上に自動編集を足す。

## Purpose / Big Picture

組立の「作る・直す」画面では、現場がメールで送った短い作業動画を素材棚に取り込み、手で範囲を切り出し、時刻付きのコメント(字幕)を付けて要領書のページに紐づけている。この作業は今すべて人手である。

この計画が終わると、動画が取り込まれて再生できる状態(READY)になった時点で、AI が映像から「どこで作業の場面が変わるか」と「各場面で何をしているか」を読み取り、場面の区切りと字幕の**案**を作る。字幕は音声からではなく映像から作る(動画は取込時に音声を捨てている)。利用者は動画棚で案を見て、そのまま採用するか、直してから採用する。採用した内容は今ある場面(ProcedureVideoScene)とコメント字幕(ProcedureVideoComment)として保存され、再生画面に今までどおり表示される。

あわせて、AI の案と人が確定した内容の両方を記録する。これで「案のうち何割がそのまま使われたか」を測れ、後の段階では確定済みの例や現場の用語を AI への指示に混ぜて、投稿が増えるほど案が業務に合っていく流れを作る。

動作の確かめ方: 素材メールで動画を1本送り、READY になってから数十秒以内に動画棚へ「AI案あり」が出ること、開くと場面の区切りと字幕の案が並ぶこと、採用すると再生画面に字幕が出ることを見る。

## 前提知識と用語

ここで使う言葉を、この文書だけで分かるように定義する。

- **動画棚**: 「作る・直す」画面上部の「動画」の一覧。Web の `ProcedureManualWorkshop.tsx` から開く。
- **ProcedureVideo**: 取り込んだ動画1本を表す DB 行(`apps/api/prisma/schema.prisma` の `model ProcedureVideo`)。状態は PENDING → PROCESSING → READY / FAILED。READY になると、長辺640・音声なし・30fps の H.264 MP4(以下 SD 動画)と先頭フレームの JPEG が保存され、元ファイルは消える。60秒を超える動画は TOO_LONG で失敗する(`procedure-video-processing.service.ts` の `durationSeconds > 60`)。
- **場面(Scene)**: `ProcedureVideoScene`。動画内の開始秒・終了秒と題名。ページへの紐づけ(`ProcedureVideoLink.sceneId`)に使える。
- **コメント字幕(Comment)**: `ProcedureVideoComment`。時刻(`atSeconds`)と80字までの文。1本に5件まで。再生画面 `ProcedureVideoPlayer.tsx` が該当時刻から4秒間、映像の上に重ねて出す。
- **紐づけの10.5秒制限**: 要領書ページへの紐づけは10.5秒以下の動画に限る(V2 の決定)。長い動画は先にトリミングする。
- **業務モデル**: DGX Spark 上の vLLM で動く業務用の画像対応言語モデル。2026-10-16 時点の現行は `scripts/dgx-local-llm-system/model-registry.examples/business_qwen38_flash_next_nvfp4/manifest.json`(Qwen3.8-Flash-Next-NVFP4、`maxNumSeqs` 1、つまり同時に1件しか処理しない)。API からは `apps/api/src/services/inference/inference-runtime.ts` が組み立てる業務用の推論経路(OpenAI 互換の `/v1/chat/completions`)で呼ぶ。現行のアダプター `routed-vision-completion.adapter.ts` は1回に画像1枚しか送らない。
- **JEV**: TypeSafe 社の判定 API(`https://api.typesafe.ai/v1/systemone`)。文章と画像を渡し、用意した選択肢のどれに当たるかを確率付きで返す。素材のページ分割案で既に使っている(`procedure-material-split-suggestion.service.ts`、env は `TYPESAFE_API_KEY`)。作業動画の静止画を送ることは 2026-10-16 にユーザーが承認済み。
- **後回し実行(background)**: 推論呼び出しに `background: true` を付けると、画面操作から来る要求より優先度を下げて流す。素材画像の説明生成(`procedure-material-image-description.service.ts`)が同じ方式を使っている。

## 調査と試験で分かったこと

2026-10-16 に、素材棚のサンプル動画(37秒、0〜14秒は動きなし、14.5秒から上から細い棒が降りてくる、36秒でカメラが引く)で試験した。静止画は1秒ごとに37枚切り出した。本番の設定とデータは変えていない。

業務モデルに37枚を1回でまとめて渡し、区切りと字幕を JSON で返させた結果、区切りは 0-15 / 16-35 / 36 秒で正解とほぼ一致した(約14秒、入力約8,500トークン、画像1枚あたり約220トークン)。字幕は「カメラの引き」は正しかったが、「測定器の位置合わせと準備」は推測が混ざり、「ドリルによる穴あけ加工」は誤りだった。区切りは得意、字幕の言葉選びは自由に書かせると外れる、という結果である。区間ごとに字幕だけを作らせると1区間約4秒だった。複数画像を1回で送れることもこのとき確かめた。

JEV に隣り合う1秒間隔の2枚を見せ「場面が変わったか」を選ばせると、すべて0.05以下で切れ目を一つも見つけられなかった。5秒間隔にすると棒の出現で0.27(jev-1.13.0)/0.24(jev-1.14.0)、カメラの引きで0.07/0.14と相対的な山は出たが、判定基準の0.5には届かない。一方、区間の静止画を渡して用意した字幕候補から選ばせると、0〜14秒は「動きなし」0.74、15〜35秒は「棒が降りてくる」0.88で正解し、誤りの「ドリル」は0〜0.01と確実に退けた。

外部の知見では、日立が2026-09に発表した研究は「手順リストと照らし合わせて区切る」方式で、自由記述より手順の候補から選ぶほうが安定するという今回の結果と合う。IKEA-Bench や LEGO Co-builder などの評価では、何も教えないままの画像言語モデルは組立作業の理解が弱いと報告されている。tebiki などの国内製品は音声からの字幕が中心で、映像からの字幕は今回の要件に合わない。NVIDIA の VSS(動画検索と要約の参考構成、DGX Spark 対応)は大規模すぎるため、考え方だけ参考にする。

この結果から役割を次のように分ける。業務モデルが区切りと字幕の下書きを作る。JEV は字幕の下書きを確かめ、手順リストなどの候補がある場合はそこから選ぶ。最後に人が直す。

## Plan of Work

### リリース時の最小範囲(段階 A)

段階 A の目的は、投稿された動画ごとに案を自動で作り、人が直して確定し、その差を記録することである。業務モデルの呼び出し方と画面の流れを本番で固めることを優先し、学習の仕組み(過去例を指示に混ぜる)は入れない。

**データ**: expand-only の migration で `ProcedureVideoAutoEditSuggestion`(仮名)を1テーブル足す。列は、動画 ID、状態(PENDING / RUNNING / READY / FAILED / SKIPPED)、試行回数、使ったモデルと経路の識別子、指示文の版、AI の案(場面の配列と字幕の配列を JSON で)、JEV の確認結果(JSON、任意)、確定内容(JSON、確定時に保存)、確定日時、エラー内容。動画1本につき最新の1行を有効とし、作り直したときは古い行を残す。既存の ProcedureVideo / Scene / Comment の列は変えない。

**起動**: 動画が READY になった処理の直後(取込、トリミング、接続のどれでも)に、提案行を PENDING で作る。既存の毎分のスケジューラーに相乗りする提案 worker が、最古の PENDING を1件だけ取り、条件付き claim で同時1件に保つ。動画変換の worker とは別の排他にする(変換を止めないため)。失敗は3回まで PENDING に戻し、4回目で FAILED。業務モデルが止まっている(接続エラーや502)ときは試行回数を増やさずに次の周期へ回す。環境変数 `PROCEDURE_VIDEO_AUTO_EDIT_ENABLED` が false なら何もしない(既定は false で出し、確認後に true にする)。

**静止画の切り出し**: SD 動画から ffmpeg で1秒に1枚、長辺640の JPEG を一時領域に切り出す(60秒以下なので最大61枚)。transcoder port に `extractFrames` を足し、テストではモックにする。終わったら一時領域を消す。

**業務モデルの呼び出し**: inference の vision 経路に「複数画像を1回で送る」入口を足す。既存の1枚用の呼び出しは変えず、画像配列を受ける別メソッドとして追加する。`background: true`、`enable_thinking=false`、温度0、タイムアウト120秒。指示文は「各画像の時刻(秒)」「区切りの開始秒・終了秒・場面の題名(20字以内)・字幕(40字以内、見えている動作だけを書き、道具名や目的を推測しない)」を JSON で返すよう求め、その画面の機種名・工程名・ページの見出しなど、既に分かっている文脈を添える(`procedure-site-context.ts` にある現場文脈の扱いに合わせる)。返ってきた JSON は型を検証し、区切りが動画の長さに収まるよう丸める。場面は動画1本につき最大5件、字幕は今の上限(5件・80字)に収める。

**JEV による確認**: 業務モデルの字幕案ごとに、その区間から3枚(始め・中・終わり)を選び、「この字幕は映像と合っているか」を、字幕案と「動きなし」「カメラの移動」「その他の作業」を選択肢にして JEV に聞く。字幕案の確率が低い(初期値0.3未満、記録を見て調整)場合は案に「要確認」の印を付けるだけで、字幕そのものは書き換えない。JEV が使えない場合は確認を飛ばして案を出す(確認は必須にしない)。1本あたりの JEV 呼び出しは最大5回。

**画面**: 動画棚の各動画に「AI案あり」「AI案を作成中」「AI案なし」を小さく出す。READY の動画を開いたとき、案があれば場面と字幕の一覧(時刻、題名、字幕、要確認の印)をプレイヤーの横に出し、各行をタップするとその時刻へ飛ぶ。行ごとに文を直す・消すができ、「採用」で場面とコメント字幕へ一括保存、「使わない」で案を閉じる。既存のコメントがある動画では、採用前に「今のコメントを置き換えます」と確認する。保存は既存のコメント PUT と同じ権限と検証(5件、1〜80字、0〜長さの範囲)を通す。キオスクの UI 規則(画面いっぱいに伸ばしたボタンや長い説明文を置かない、アイコンと短い言葉)に従い、作る前にモックを出して確認を取る。

**記録と効果測定**: 採用時に確定内容を保存する。案と確定内容を比べて、場面ごと・字幕ごとに「そのまま」「直した」「消した」「人が足した」を数える集計を API の内部関数として持ち、管理用のエンドポイントまたはスクリプトから読めるようにする。字幕の「そのまま率」と区切りの時刻のずれ(秒)を主な指標にする。

### 後から足す範囲(段階 B 以降)

段階 B: 確定済みの例を指示文に入れる。同じ機種・工程の確定済み字幕の上位数件と、人が直した言葉の対(例:「棒」→「ガイドピン」)を集めた用語集を作り、業務モデルの指示文と JEV の選択肢に加える。手順リスト(要領書のそのページの手順文)が分かる動画では、字幕を自由記述ではなく手順文から JEV に選ばせる。指示文の版を上げ、段階 A の指標と比べて効果を確かめる。

段階 C: 長さと件数の上限を見直す。60秒の取込上限、字幕の5件・80字の上限、紐づけの10.5秒制限を、実際の投稿の長さと確定内容の分布を見て必要なら広げる。長い動画では、AI の区切りから「この範囲でトリミング」を1操作で要求できるようにする(V2 のトリミング API を使う)。

段階 D: 手で組み立てる動画など、カメラの前で手が細かく動く動画で再試験する。サンプル動画は機械の動きが中心だったため、手作業での字幕の当たり方は未確認である。結果次第で、静止画の間隔(1秒より細かく)や、業務モデルではなく JEV を主にする場面を決め直す。

## Concrete Steps

段階 A の作業順は次のとおり。各段で `cd apps/api && pnpm lint && pnpm exec vitest run procedure-video && pnpm exec tsc -p tsconfig.build.json --noEmit`、画面の段では `cd apps/web && pnpm lint && pnpm exec vitest run procedure-manuals && pnpm build` を通す。

1. migration と Prisma モデルを足し、提案行の作成と状態遷移のサービスを書く。READY 化の3経路(取込・トリミング・接続)から作成を呼ぶ。
2. transcoder port の `extractFrames` と ffmpeg 実装、モックのテスト。
3. inference に複数画像の入口を足し、業務モデル用の指示文と JSON 検証を書く。不正な JSON、長さを超える区切り、上限超過の丸めをテストする。
4. JEV 確認の呼び出し(`procedure-material-split-suggestion.service.ts` の作りを手本にする)と、使えないときに飛ばすテスト。
5. 提案 worker をスケジューラーに登録し、claim、再試行、業務モデル停止時の扱い、無効化フラグをテストする。
6. API: 提案の取得、採用(確定内容の保存とコメント・場面の置き換えを1つのトランザクションで)、使わない、作り直し。
7. 画面のモックを出してユーザーの確認を取り、動画棚の表示と案の一覧・採用の流れを作る。
8. 集計関数と読み出し口。
9. 本番で `PROCEDURE_VIDEO_AUTO_EDIT_ENABLED=false` のまま反映し、サンプル動画で手動の作り直しを1回試してから true にする。

## Validation and Acceptance

段階 A の受け入れ条件:

- 動画が READY になると、業務モデルが動いていれば数分以内に提案が READY になる。業務モデルが止まっていても動画の取込と再生は影響を受けず、再開後に提案が作られる。
- サンプル動画(37秒)で、区切りの開始秒が正解(0秒、14.5秒前後、36秒)から±2秒以内に収まる。字幕はドリルのような見えていない作業を書かない。
- 採用すると再生画面に字幕が出て、既存のコメント上限と検証を必ず通る。使わないを選ぶと何も保存されない。
- 案と確定内容の差を集計で読める。
- 無効化フラグが false のとき、提案行も推論呼び出しも作られない。

## Idempotence and Recovery

提案の作成は動画1本・READY 化1回につき1行で、同じ動画の作り直しは新しい行を足すだけなので、何度実行しても既存の場面・コメントは採用操作をしない限り変わらない。migration は列とテーブルの追加だけで、戻すときはフラグを false にすれば機能が止まる。一時領域の静止画は worker の終わりに必ず消し、異常終了で残った分は次回起動時に古いものから消す。

## Interfaces and Dependencies

- 業務用の推論経路(`inference-runtime.ts`)に複数画像を送る入口を足す。既存の1枚用の呼び出しと env の意味は変えない。DGX Spark 側の Control Plane の API やモデル定義は変えない。
- JEV は既存の `TYPESAFE_API_KEY` を使い、新しい秘密情報は足さない。画像は最短辺256px以上で送る。
- 業務モデルは同時1件なので、すべての推論は `background: true` で流し、画面からの要求を待たせない。

## Surprises & Discoveries

- JEV は隣り合う1秒間隔の静止画では場面の変化をまったく拾えなかった(全て0.05以下)。間隔を5秒にすると相対的な山は出たが、判定基準には届かない。証拠: 2026-10-16 の試験。区切りは業務モデルに任せる。
- 業務モデルは37枚を1回で受け取れ、全体を見せると区切りが安定した。一方、字幕を自由に書かせると見えていない作業(ドリル)を書くことがある。
- JEV に渡す静止画の組み方が悪いと(カメラの引きの直前の区間を混ぜると)、正しい選択肢の確率が下がった(棒0.55 / カメラの引き0.32)。区間の端の数枚を確実にその区間内から取る必要がある。
