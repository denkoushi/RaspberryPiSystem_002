# 似た図面から丸数字を「意味で」写す（業務LLM 版）

この ExecPlan は `.agent/PLANS.md` に従う生きた文書である。進捗、発見、判断を作業のたびに更新する。旧方針（丸数字を付ける理由を規則にする rule-v1）は本書で置き換える。

## Purpose / Big Picture

検査図面に丸数字（検査箇所）を付ける作業を、似た過去図面の丸数字一式を写すことで省く。写すのは「図面全体の形が似ているときだけ」で、似ていなければ案を出さない。写し方は寸法の数値ではなく「その丸数字が部品のどこの何を測っているか」で対応づけ、数値は写し先の図面のものを使う。部位ごとに図面を比べることはしない。

完成すると、管理画面で新しい図面を開いたとき、形の似た過去図面があれば丸数字の案が並び、検査員は直すだけで済む。直した内容は記録され、夜間の振り返りで業務LLM への決まりとお手本が増え、使うほど精度が上がる（閉じた輪）。

## Surprises & Discoveries

- 形は似ていても寸法の数値は必ず違う。数値の近さで写す現行 `transferItems` は使える案がほとんど出なかった。
- 業務LLM は似ていない図面でも丸数字をほぼ全部置いてしまう。「置けた割合」は門番にならない。門番は似ている度だけに頼る。
- 本番の問い（同じ部品系列か）では、名前が同じで形が違う組に 0.95、形の似た左右対に 0.15 が付いた。形だけを比べるよう指示すると 0.4 / 0.7 になった。
- 業務LLM は思考オフでも本文で長く考え始め、JSON を出し切らないことがある。「考えた過程は書かず最初の文字から JSON」「role を15字以内」と指示すると収まった。1組あたり約1〜2分。
- 画像の濃さによる前段しぼりは、左右対や大きさ違いはほぼ上位に残すが、ベアリングサポート同士のように図の描き方が違う組は下位（23/29位）に落とすことがある。(2026-11-01)
- 本番コンテナは rootfs 読み取り専用で、`docker cp` は失敗する。試験は tmpfs の `/tmp` へ tar で流し込んで動かした。blue/green 切替でコンテナ名が変わると試験が止まる。
- 業務LLM の残る置き間違い: かっこ付きの参考寸法、同じ寸法への重複、幾何公差の種類と枠の不一致、深さと径の取り違え、粗さ記号や注記文字への配置。

## Decision Log

- 前段しぼりの既定を8から12に上げる。理由: 本番試験で8件だと似た組22通り中4通りが落ち、12件で2通りに減る。全件（29件）送ると全図面で約5時間になり夜間の枠に重い。日付: 2026-11-01。
- M1 では写しの版 `PART_MEASUREMENT_DRAWING_PLACEMENT_VERSION` を上げない。上げると今の数値一致の写しで全図面の案を作り直すだけになるため。既に案がある図面は M2 で版を上げるまで旧い案のまま。日付: 2026-10-29。

- 図面全体の形で似ている度を判定し、0.8以上だけ写す。理由: 71組で誤って通るのが1組、取りこぼしは4組。0.85 は誤りゼロだが似ている組が4組しか通らない。日付: 2026-10-29。
- 対応づけは業務LLM が行い、JEV は使わない。理由: 上記の試験結果。日付: 2026-10-28。
- 評価は過去の人の印との一致率で行わない。図面ごとに Fable（判定役）が「検査員として使えるか」を判定する。日付: 2026-10-28。
- 強い先生役（Opus / Fable）の考え方は、お手本と決まりの文章として業務LLM に渡す（LEAP、kNN お手本）。本当の追加学習（LoRA）は正解が数百組たまってから検討する。日付: 2026-10-28。
- 業務LLM が答えられないときは案を出さない（名前フォールバックや JEV で代わりに写さない）。理由: 誤った写しは手で付けるより手間が増える。日付: 2026-10-29。
- 見本方式（reference-v1、一般的な決まりだけで似た図面なしに案を出す）は使わない。フラグ `INSPECTION_DRAWING_REFERENCE_PLACEMENT_ENABLED` は有効にせず、M2 で見本方式の案を優先表示する分岐と夜間処理を外す。理由: その部品で人が選んだ箇所に基づかず、評価も人の印との一致率でしか示されていない。似た図面がなければ案を出さない。日付: 2026-10-29。

## Plan of Work

M1 形の似ている度。`SIBLING_VISION_INSTRUCTIONS` を形だけを比べる問いに替える（図面名・表題欄・注記を見ない。外形、図の並び、穴の並び、主な形状を順に比べてから 0〜1 を出す）。採用条件を `shapeSimilarity >= 0.8` にし、`SIBLING_MATCH_VERSION` を上げる。試験は1対1で測ったため、本番の「候補をまとめて送る」形でも同じ値が出るかを先に確かめ、ずれるなら1対1で呼ぶ。迷ったときの JEV 回り道（固定 0.7）は 0.8 に届かず実質無効になるため外す。

M1 では次も合わせて直す。(a) 前段しぼり `prefilterDrawingSiblings` は「寸法の数値一致」か「図面名の系列」で上位8件に絞るため、形が似て数値も名前も違う図面が候補から落ちる。数値一致をやめ、形で選べる前段（例: 同じ工程・同じ顧客の図面から縮小画像で業務LLM に広く当てる、または画像の特徴量で近い順）に替え、71組の正解組が前段を通るかを受け入れ条件に入れる。(b) 業務LLM が3回失敗したときの名前フォールバック（固定 0.4）は今も MATCHED になり、しきい値を素通りする。失敗時は「案なし」にし、名前で写さない。DGX 停止中は JEV に逃がさず、翌晩に再試行する。(c) `SIBLING_MATCH_VERSION` を上げると全図面が夜間バッチ（30件/回）で判定し直しになる。件数と所要時間を先に数え、DGX の裏作業枠に収まるかを確かめる。

M2 意味で写す。`transferItems` の候補選びを業務LLM による対応づけに置き換える。入力は、元図面（人の丸数字入り）、写し先図面に DimensionMap の各寸法へ D 番号を赤で描いた画像、丸数字一覧（工程、項目、値）、D 番号一覧。出力は `{"items":[{"n":1,"role":"上面図 全幅","target":"D3"}]}`（置けないときは `target: null`）。丸数字は選んだ寸法の位置に置き、値は写し先の寸法から読む（「深」を含む項目は深さの値）。公差は元の上下の幅を保つ。機能フラグで旧方式に戻せるようにする。

M2 では次も合わせて直す。(a) 提案行の値は今 `ensureRun` が写し元の項目から書いているため、`PlacementTransferResult` とサービスの行生成も写し先の値を持つよう変える。既存項目との重複判定 `placementItemAlreadyExists`（名前＋値）も写し先の値で判定する。(b) `PART_MEASUREMENT_DRAWING_PLACEMENT_VERSION` を新しい版にし、旧版のランと混ざらないようにする（旧方式へ戻すときは旧版キーのランが使われる）。(c) 失敗時: タイムアウト（現行 115 秒）や壊れた JSON は全件 UNPLACED のランとして保存し、毎晩同じ図面を呼び続けない。再試行は版が変わったときだけ。maxTokens は応答時間に収まる値を試験で決める。(d) 管理画面は見本方式（`INSPECTION_DRAWING_REFERENCE_PLACEMENT_ENABLED`）の案があると写し方式の案を隠す。見本方式は使わないため、この優先分岐と見本方式の夜間処理を外し、フラグを無効のままにする（本番 inventory の値を先に確かめる）。

M3 チェック（プログラム）。業務LLM の答えに対し、次を機械的にはじいて UNPLACED（人が付ける）にする: かっこ付きの参考寸法、同じ寸法への重複（幾何公差の枠を除く）、幾何公差の項目なのに枠でない寸法、深さの項目に径の寸法、粗さ記号や注記の文字。判定は DimensionMap の種類と文字列から行う。

M4 お手本と決まり。Fable が「使える」とした Opus の対応づけをお手本集にする。写し元・写し先の組に最も形の近いお手本を1件、文字（丸数字と D 番号の対応と role）で指示に添える。加えて、業務LLM の間違いと Opus の正解を並べ、Opus / Fable に短い決まりを書かせて指示に入れる。お手本と決まりは版付きのファイルにし、戻せるようにする。

M4b 案を動かせる画面（利用者の実機確認 2026-10-29 による）。今、案の点線丸数字（`InspectionDrawingCanvas.tsx` の案ボタン）は選択しかできず、ドラッグできない。確定丸数字のドラッグ処理（同ファイルの `handlePointPointerDown` 以降）を案にも使い、案を動かせるようにする。動かした位置は採用時の確定丸数字の位置になる（`useInspectionDrawingPlacementProposals.ts` で `row.markerXRatio` の代わりに動かした位置を渡す）。採用の記録（decisions）に最終位置を含め、AI 案の元の位置と人が動かした位置の両方を DB に残す（M5 の migration と同じ列）。これで「AI がどこに置き、人がどこが正解としたか」が学習に使える。
あわせて、この編集は今キオスク専用画面（`/kiosk/part-measurement/inspection/create` と `templates/:templateId/edit`、キオスクの没入レイアウト）でしかできない。通常の利用者が PC のブラウザでフル画面のまま同じ編集（案の採用・移動・却下と丸数字の追加）をできる経路を用意する。同じ部品（Canvas、案パネル、フック）を使い、画面だけを分ける。

M5 閉じた輪。最初の作業は DB 変更: 提案の状態は今 PROPOSED/APPROVED/REJECTED/UNPLACED だけで、`recordDecisions` は採用と却下しか残さない。最終位置（移動）、案に無かった追加項目、業務LLM の `role` を残す列を migration で足す。そのうえで検査員が案を採用・移動・削除・追加した記録を残す。夜間に直された箇所を集め、先生役が決まりとお手本の追加案を作る。採点用の組（今回の26組と71組から始めて増やす）で業務LLM を採点し、悪くならなかったときだけ新しい版を採用する。先生役に本番の図面画像を社外（Opus / Fable）へ送るかは利用者の判断待ち（現在の社外送信の承認は TypeSafe/JEV のみ）。送れない場合は、業務LLM 自身と文字情報だけで振り返る。
