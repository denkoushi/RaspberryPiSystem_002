# キオスクお問い合わせ受信箱 Runbook

キオスクの「お問い合わせ」は Slack に通知されるが、着信を見落としやすい。そこで、指定した端末のフローティングChat(画面右下の丸ボタン)で着信を受け、その場で読んで返信できるようにした。Slack 通知と `ClientLog` への保存は今までどおり残る。

## 動き

- 新規送信はフローティングChat(右下の丸ボタン)の「お問い合わせ」→「＋ 新規」から行う。ヘッダーの「お問い合わせ」ボタンは撤去した。
- 受信端末でも新規送信に社員証は不要。未解錠のまま送信すると「送信しました」と表示してロック画面へ戻り、閲覧には引き続き社員証が必要。
- 送信者を選んで「送信」を押す。依頼は「現場まで来てください。」を初期値に自由入力できる(200文字まで、空欄は送信不可)。時計ボタンからこの端末の送信成功済みの依頼履歴を選べる。履歴はブラウザの localStorage に新しい順・重複なしで10件まで記憶し、定型文は常に先頭へ表示する。「日時・詳細」は任意で、閉じていると日時を送らない。送信失敗時は入力を保持し、その場にエラーを表示する。
- 「お問い合わせ」表示中はパネルの標準幅が560pxに広がる(狭い画面では縮小、高さは従来どおり)。2倍表示を選んでいる場合はそちらを優先する。
- 送信側端末では送信後に一覧を更新し、送ったスレッドを開く。

| 端末 | 丸ボタン | 開き方 |
| --- | --- | --- |
| 受信端末(管理コンソールで指定) | 未読のお問い合わせがあるとオレンジ＋件数 | 押して社員証をタッチ。登録済みの社員番号だけ開ける |
| 送った端末 | 返信が届くとオレンジ＋件数 | 押すだけ。その端末から送った分だけ読める |

- 未読があるときに丸ボタンを押すと「お問い合わせ」表示で開く。未読が無いときは今までどおり開き、「お問い合わせ」はタブから選ぶ。
- 受信端末は、パネルを閉じるか別のタブへ移ると鍵がかかった状態へ戻る。社員証の UID は画面を開いている間だけメモリに持ち、保存しない。
- 登録されていない社員証、未登録のタグ、在籍していない社員は、区別せず「この社員証では開けません」になる。
- 返信すると相手側が未読になる。送った端末からの追記は Slack にも届く。受信端末からの返信は Slack に送らない。
- 件数は 30 秒ごとに更新する。問い合わせるのは `/kiosk` 配下の画面だけで、管理画面やサイネージでは丸ボタンは今までどおり。
- 一覧は受信端末で新しい順に 50 件、送った端末で 20 件まで。それより古い分は画面に出ない(DB には残る)。
- この機能を入れる前のお問い合わせ(`ClientLog` だけの行)は受信箱に出ない。
- 送信フォームの送信者は、先に部署を選んで絞る。部署は社員マスタの「セクション」(例: 機械課)で、セクションが空の社員だけ「部署」(例: 製造部)で代用する。開いたときは名前に「機械課」を含むものが選ばれている(無ければ先頭)。どちらも空の社員は「部署なし」にまとまる。
- 部署は「機械課」「製造課」「組立」を名前に含む課(組立1課・組立2課など)を優先表示し、その他は「⋯」で開閉する。畳んでも選択中の課は残り、優先表示に該当する部署が無ければ全部署を表示する。
- 送信者を選ぶと他の名前は隠れ、依頼までスクロールなしで届く。選んだ名前をもう一度押すと解除され、全員が戻る。
- 送信者は約250msの長押しドラッグ、またはフォーカスしたボタンで Alt+←/→ により並べ替えられる。順序は部署ごとにこの端末のブラウザの localStorage へ記憶する。

## 設定(管理コンソール)

`/admin/kiosk-settings` の「お問い合わせの受信」で設定する。権限は ADMIN または MANAGER。

1. 「受け取る端末」で通常のお問い合わせを受ける端末にチェックを入れる。端末ごとの「システム通知」は独立した設定で、両方または片方だけを選べる。
2. 「開ける人(社員番号)」に社員番号を入れて「追加」。社員マスタにある番号だけ追加でき、氏名が横に出る。
3. 「保存」を押す。保存は全置換で、端末は次の件数更新(30 秒以内)から切り替わる。

両方の受信設定を全端末で外すと、新たな受信通知は出ない。自端末から送ったお問い合わせの返信は引き続き確認できる。社員番号を 1 つも登録しないと、受信端末でも誰も開けない。

## システム通知

- 端末の不調は同じ受信箱に短い日本語で表示する。例: `StoneBase01 バーコードリーダー` / `バーコードリーダーが応答しません。`。端末名は `statusClientId` で紐づく `ClientDevice.location`、未設定なら `name（clientId）`(例: `Mac（mac-kiosk-1）`)を使う。空き容量と温度の本文には数値を入れる。未復旧の行の題名は、登録名を変えると次の評価で更新される(未読にはしない)。
- 未復旧は「システム」、復旧後は「復旧」の小さなタグが付く。復旧時は「復旧しました。」を追記して未読にする。
- 通常のお問い合わせは従来の受信設定、システム通知は「システム通知」を有効にした端末だけに届く。どちらかが有効なら閲覧・返信に登録済み社員証が必要で、「開ける人」のリストを共用する。
- 「交換しました」などのメモを返信できる。システム通知とその返信は Slack に送らない。システム通知だけを受信する端末も、自端末から送った通常のお問い合わせは送信者として閲覧・追記できる。
- 同じ不調では未復旧スレッドを1つだけ保持する。同じ状態が続いても、システムの前回投稿から24時間未満は追記・未読化しない。社員のメモ投稿はこの間隔に影響しない。復旧後の再発は新しいスレッドになる。

| 通知元 | 条件 / 復旧 |
| --- | --- |
| 周辺機器の既存Alert | バーコード・社員証リーダー・トルク測定器の不調。端末＋機器＋信号でまとめ、既存の復旧報告で復旧通知する |
| 保存装置のAlert | 既存のAlert判定を利用し、端末＋信号でまとめる。以下の文言を使い、未知の信号は「保存装置」/「保存装置の確認が必要です。」。復旧報告がないため自動復旧しない |
| `root_filesystem_read_only` | 「SDカード」/「SDカードに書き込めなくなっています。」 |
| `kernel_storage_error` | 「SDカード」/「SDカードで読み書きの失敗が出ています。」 |
| `ext4_errors_recorded` | rootのext4 `errors_count` が0より大きい場合。「SDカード」/「SDカードに異常の記録があります。」 |
| `storage_write_rate_high` | 「SDカード」/「SDカードへの書き込みが多くなっています。」 |
| `power_undervoltage_current` / `power_undervoltage_since_boot` / `power_throttled_current` | 「電源」/「電源の電圧が下がっています。」 |
| `root_inode_usage_high` | 「空き容量」/「保存できるファイル数の残りが少なくなっています。」 |
| `root_disk_usage_high` | Alertからの通知は送らず、下記「保存領域」の定期評価だけで通知する（二重通知を防ぐ） |
| 画面の既存Alert | 既存のAlert判定を利用し、端末でまとめる。復旧報告がないため自動復旧しない |
| ファイルから取り込むAlert | 種類ごとにまとめる。例: 日次の `rkhunter-warning`。最後の発生から48時間再発がなければ、投稿・未読化せず閉じる（表示タグは「復旧」）。同じファイルの再取り込みは再発として数えない |
| 端末からの連絡 | 最終報告から15分以上で通知、新しい報告で復旧 |
| 保存領域 | 使用率90%以上で通知、90%未満で復旧 |
| 端末温度 | 80°C以上で通知、80°C未満で復旧。温度未取得の場合は判定しない |

`ClientStatus` の評価とファイル通知の期限確認は約5分ごと。14日以上報告のない端末は評価しない（既存通知もそのまま残す）。通知の保存失敗はログに残し、端末の報告受信とAlert保存を妨げない。テスト中は定期実行しない。

止めるときは `/admin/kiosk-settings` の対象端末の「システム通知」を外して「保存」する。すべて外せば通知の表示を停止できる。通常のお問い合わせ受信、元のAlert、DB上の通知履歴は残る。既存Slack配送の変更はない。

## 確認手順(実機)

1. 現場のキオスクで丸ボタン→「お問い合わせ」→「＋ 新規」を開き、送信者を選んで送る。
2. 受信端末の丸ボタンが 30 秒以内にオレンジになり、件数が出る。
3. 押して、登録した社員の社員証をタッチすると一覧が出る。登録していない社員証では開けない。
4. スレッドを開いて「行きます」などを送ると、受信端末の件数が減り、送った端末が 30 秒以内にオレンジになる。
5. 送った端末で押すと、社員証なしで返信が読め、追記できる。

## 実装の場所

- DB: `ClientDevice.inquiryReceiverEnabled` / `systemNoticeReceiverEnabled`、`KioskInquiryReceiverEmployee`、`KioskInquiryThread`、`KioskInquiryMessage`(migration `20261009090100_add_kiosk_inquiry_inbox`。追加だけで既存の列と行は変えない)
- API: `apps/api/src/routes/kiosk/inquiries.ts`、`apps/api/src/routes/kiosk-settings.ts`、`apps/api/src/services/kiosk-inquiry/`。スレッドは `POST /kiosk/support` の `ClientLog` 保存と同じトランザクションで作り、応答は既存の `requestId` に `threadId` を追加して返す
- Web: `apps/web/src/features/kiosk/inquiry/`、入口は `apps/web/src/components/hermes/HermesFloatingChat.tsx`。送信フォームは `apps/web/src/features/kiosk/inquiry/KioskInquiryCompose.tsx`

## うまくいかないとき

- オレンジにならない: その端末で対象種別の受信チェック（通常のお問い合わせ / システム通知）が有効か、画面が `/kiosk` 配下かを確認する。API は `GET /api/kiosk/inquiries/summary`(`x-client-key` 付き)で `isReceiver` と `unreadCount` を返す。
- 社員証で開けない: 社員番号が「開ける人」にあるか、その社員が在籍(ACTIVE)か、社員証のタグがその社員に登録されているかを確認する。
- 元へ戻す: Web と API を前の版へ戻せば受信箱は消える。追加したテーブルと列は残しても既存の動作に影響しない。
